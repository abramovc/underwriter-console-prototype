How Intuition works.

Intuition is the internal decision support layer that translates workflow tags and provider-native signals into clear underwriting themes, recommended actions, and a decision-first review surface. This page documents the current state of the system, where the source of truth lives, and how to edit the system safely.

View Intuition

Current state

Today, Intuition takes raw and formatted provider responses, normalizes them into canonical concepts, groups them into underwriting insight buckets, and then surfaces a top recommended action plus supporting actions for the underwriter.

Current goals

  • Make manual review easier to understand.
  • Translate raw tags and reason codes into clearer underwriting language.
  • Keep the logic editable without making production behavior fragile.
  • Separate collaboration from production source of truth.

Current output layers

  • Canonical concepts — normalized meaning for raw provider signals.
  • Canonical insights — grouped underwriting themes such as Business Legitimacy or Contactability.
  • Recommended actions — suggested next steps for applicant, underwriter, or system.
  • Decision summary — hero headline, primary driver, and additional recommended actions.

Source of truth

Best practice for this system is to keep production truth in code and use a shared spreadsheet as the collaboration layer. The spreadsheet is where the team proposes and discusses changes. The repository is where approved changes are implemented, versioned, tested, and deployed.

Layer Purpose Current owner
Google Sheet Collaboration, comments, proposals, review. Product / Risk / internal team
CSV + JS in repo Production source of truth. Engineering implementation
Intuition UI Rendered decision support experience. Engineering

Rule: the Google Sheet is not the production source of truth. It is the collaboration layer. Production behavior should only change after the corresponding code or CSV files are updated, tested, committed, and deployed.

Editing workflow

The safest workflow is: discuss in the sheet, implement in code, validate in Intuition, then deploy.

  1. Propose a change in the shared Google Sheet.
  2. Review the change for meaning, impact, and naming consistency.
  3. Implement the approved change in the repo.
  4. Test with representative payloads in intuition.html.
  5. Commit, push, and verify in production.

This keeps collaboration open while preserving version control, rollback capability, and a clean audit trail.

Canonical concepts

Canonical concepts are the normalized meanings assigned to provider tags, reason codes, and raw review signals. They are the base layer of the system. If a provider returns a raw signal, Intuition should try to map that signal to a canonical concept before it does anything else.

Current concept groups

Group What it covers
Identity Name, DOB, SSN, mismatch, deceased, unresolved identity signals.
Fraud Synthetic identity, fraud risk, velocity, frequency anomalies.
Contact Email, phone, address risk and supporting verification signals.
Bank Bank validity, ownership match, ownership mismatch, unknown bank state.
Compliance Watchlist, sanctions, PEP, adverse media, supporting compliance signals.
Business Business legitimacy, registration, status, high-risk industry, mismatch.
Credit / Legal Credit outcomes, bankruptcy, liens, litigation.

Current source

canonical-schema/mappings/concept_dictionary.csv

Editing guidance

  • Add a new concept only if an existing concept does not already cover the meaning.
  • Prefer stable names over provider-specific wording.
  • Do not silently change meaning of an existing concept.
  • If the concept meaning changes materially, re-test affected payloads.

Canonical insights

Canonical insights are the underwriting themes shown in the Intuition UI. These are bucketed views of the normalized signals, designed to help an underwriter understand what kind of concern is being surfaced.

Insight Purpose
Identity Integrity Is the applicant identity real, consistent, and attributable to one person?
Contactability Can we reliably reach and verify the applicant?
Fraud / Velocity Are there abuse, synthetic identity, or repeated-attempt patterns?
Compliance Screening Are there sanctions, watchlist, PEP, or other compliance concerns?
Business Legitimacy Does the business appear real, registered, and consistent across sources?
Bank Ownership Does the payout account belong to the applicant or business?
Positive Verification What evidence increases confidence in the application?
Other Signals Signals that do not yet fit a cleaner underwriting bucket.

Current source

underwriter-console-prototype/js/insightBuckets.js

Bucket behavior

Buckets do two things: they group signals into an underwriting theme, and they define a default set of recommended actions for that theme.

Recommended actions

Recommended actions are the next-step suggestions surfaced by Intuition. They are intentionally structured around audience so the system can distinguish between something the applicant should do, something the underwriter should do, and something the system can do automatically.

Audience Examples
Applicant Request selfie + ID verification, send text OTP, request business documents, connect bank account via Plaid.
Underwriter Escalate manual review, escalate fraud review, escalate compliance review, escalate business review.
System Order state registration documents, run additional verification.

Current source

underwriter-console-prototype/js/recommendedActions.js

Current selection model

  • Top recommended action should align with the primary driver bucket.
  • Additional recommended actions should support the same dominant theme first.
  • Low-severity monitor buckets should not overpower the hero action.

Mapping library

Provider mappings are where raw external inputs are translated into canonical concepts. This is one of the highest leverage parts of the system because mapping quality directly affects summaries, actions, and decision clarity.

Current mapping files

File Purpose
provider_mapping_alloy.csv Maps Alloy workflow tags into canonical concepts.
provider_mapping_socure.csv Maps Socure reason codes into canonical concepts.
provider_mapping_id_analytics.csv Maps ID Analytics codes and signals into canonical concepts.
provider_mapping_lexis_nexis_instant_id.csv Maps LexisNexis InstantID output into canonical concepts.
provider_mapping_middesk_kyb.csv Maps Middesk KYB classifications and review signals.
provider_mapping_middesk_mcc.csv Maps Middesk MCC classifications.
provider_mapping_middesk_naics.csv Maps Middesk NAICS classifications.

Providers

Intuition currently works across workflow-level tags and provider-native data. The current system is especially shaped by Alloy tags and Middesk, Socure, ID Analytics, and LexisNexis mapping files.

Workflow layer

  • Alloy tags are outcome-oriented and often decision-adjacent.
  • They are useful, but they are not the same as provider-native evidence.
  • Intuition normalizes them so they can sit beside provider evidence.

Provider layer

  • Provider-native codes supply the raw evidence layer.
  • These signals should be translated before they are summarized for the underwriter.
  • The mapping layer is where provider-specific noise is reduced.

Concept to action

After raw signals are mapped into canonical concepts, Intuition uses concept-to-action logic to decide which follow-up steps make sense. This helps avoid generic next steps and keeps the hero action aligned with the dominant concern.

Current source

underwriter-console-prototype/js/conceptActions.js

Design goal

A business-led case should prefer business actions. A contactability-led case should prefer OTP or email confirmation. A fraud-led case can still elevate selfie + ID or fraud review when appropriate.

Intuition page logic

The Intuition page is currently a static HTML page with imported JS modules. The page is intentionally lightweight, but the logic stack underneath it is layered.

File Role
normalizePayload.js Builds the normalized review object from the input payload and provider mappings.
caseComposition.js Determines whether the case is business, contact, or mixed.
conceptGroups.js Groups supporting signals for the raw evidence display.
narratives.js Provides group-level and signal-level narrative text.
insightBuckets.js Defines canonical insight buckets and their default actions.
recommendedActions.js Defines the current action library and action priority.
conceptActions.js Maps canonical concepts to action keys.
insightSummaries.js Scores summaries, determines primary driver bucket, and selects hero and additional actions.
intuition.html Renders the final decision-first experience and the raw evidence views.

Testing guide

Any meaningful logic update should be tested against representative payloads before deployment.

Minimum test coverage

  • Manual business review payload
  • Manual contact review payload
  • Mixed business + contact review payload
  • Payload with strong positive verification
  • Payload with explicit compliance escalation

What to validate

  • Top recommended action
  • Primary decision driver
  • Additional recommended actions
  • Insight bucket severity and stance
  • Narrative readability

Editing guide

Use this section when you need to change the system without creating drift between concepts, mappings, summaries, and actions.

Change rules

  • Do not use the Google Sheet as production truth.
  • Do not silently rename a concept that already has mappings.
  • Do not add a generic action when a more specific action is available.
  • Do not change summary logic without testing at least one business and one contact payload.

Safe update pattern

  1. Propose or review the change in the Google Sheet.
  2. Update the relevant CSV or JS file in the repo.
  3. Run Intuition locally and test representative payloads.
  4. Commit with a clear message describing the behavior change.
  5. Deploy and verify the rendered output in production.

If you want to change a concept

Start with concept_dictionary.csv, then update the affected mapping files, and re-test the payloads where that concept appears.

If you want to change an action

Update recommendedActions.js and, if needed, conceptActions.js so the right concepts still point to the right action.

If you want to change a bucket

Update insightBuckets.js first, then verify how insightSummaries.js ranks that bucket in practice.

If you want to change hero behavior

Review insightSummaries.js first. Hero behavior should be driven by the dominant bucket, not by flat action priority alone.

This document describes the current Intuition system as implemented today. It should be updated whenever the schema, mapping strategy, action library, or summary logic changes materially.
